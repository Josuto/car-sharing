# Lessons and Reflections

- CC demanded to know whether a nonexistent service (i.e., Car Booking) was to consume an event (i.e., `UserCreated`) produced at user management bounded context during the implementation of the latter. The fact that CC is preemptively creating logic related to a not yet existing service denotes that I could have planned system implementation better; in a pure feature-based project this event logic would have been considered in a further step on the roadmap, where it would have actually become obvious. In more organic project management with more human design control, planning phases should be of a lower task granularity level (e.g., update all services' user table after operation on user management service), instead of being system service-oriented (e.g., Create user CRUD in user management service), as it has been the case.

- Also on the topic of events, CC decided to re-publish the event `BorrowerFlaggedAsDebtor` at the UpdateDebtorStatusHandler belonging to User Management. This event is originally published at Car Booking to inform User Management that a user is a debtor. However, its re-publication creates a confusing and useless circular event loop as there is no consumer service. When asked about the possible sources for this hallucination, CC replied that it missed asking the explicit question as part of the grill-me session, that it followed code without questioning it, and confessed that it did not read the `SPEC.md` file. Therefore, one must always make sure that CC has all it needs in the context window and must carefully analyse its suggestions.

- Even though CC created a multi-phase plan, sometimes it got confused on who must do what (and when and why). For example, before implementing the payments service (GH issue #5) CC recommended me to have the booking service emit a `BorrowerFlaggedAsDebtor` event when it it receives `PaymentProcessed(FAILED)` and cancels the booking. If CC would have had the contents of GH issue #7 (Car return and late-return debtor flagging) on its context window, then it would probably wouldn't have suffered such a confusion. Thus, it's worth having a representation of the steps (compacted if too long) in the multi-phase plan.

- Shift grill-me session left into the first prompt (multi-phase planning). Otherwise, it becomes a bit cumbersome.

- I had to insist on conciseness during doc generation.
