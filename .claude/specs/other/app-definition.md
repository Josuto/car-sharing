# Car Sharing App Definition

This document specifies a simple definition for the car-sharing app. It differentiates the features to be part of the MVP and those to be done post-MVP. Also, it defines the foundations of the MVP version implementation.

## MVP

### Description

This project consists of a car sharing app that enables car owners (referred as *owner users* or simply *owners*) to lend their cars to other people (referred as *borrower users* or simply *borrowers*).

The goal is to build the simplest but yet realistic production grade MVP version for the car sharing app.

### Services

Following the Single Responsibility principle, this is the list of services to implement:
- **User Management**: Enables user creation, update, and deletion. Also enables to declare a borrower a debtor.
- **Car Registry**: Enables owners to register their cars so that other people can borrow them.
- **Car Booking**: Enables borrowers to book (i.e., borrow) a car for a given period of time.
- **Payments**: Charges borrowers for the period of time they have booked a car.

### Business Rules

- App admins can create, update, and delete users. When creating a new user, administrators must specify the username, name, surname, and account balance of the user.
- Any user that wants to lend their car must provide the car registry service with their username, name, surname as well as the car type and registration number.
- An owner cannot remove their car from the car pool.
- An "available car" is a car that exists and that that is not currently booked.
- A borrower must first request a list of available cars to be provided by the car booking service.
- A borrower can then pick any available car of their liking for a minimum period of one day and a maximum period of fifteen days via the car booking service.
- When a borrower books a car the car is unavailable for other borrowers to book it.
- When a borrower returns a booked car the car is again available for other borrowers to book.
- Borrowers cannot borrow a second car without returning the first one first.
- The payments service must charge a booking fee to the borrower's bank account right after the car booking service finishes processing the borrower's booking request. For the time being, this booking fee is ten euro a day for all types of cars to be subtracted from the borrower's account balance.
- A borrower can return a booked car at any time, even earlier than the agreed booking period is consumed. In that case, unused days are not refunded. If a borrower returns the car later than the booking period are immediately considered a debtor and are disallowed from booking any car until further notice.

### System Interactions

- The app does not include a frontend; solely focus on the system backend services (also referred as services) and do not create any frontend application.
- App administrators are not technically users of the app; anyone that knows the URLs of the user management endpoints can invoke them without having to authenticate first.
- There are no regular user signup or login services to be considered; users directly interact with the app via REST through an API gateway using CLI commands like Curl or other tools like Postman or Bruno.
- Use synchronous REST (HTTP) for all READ operations (e.g., listing cars) and Gateway routing; reserve Kafka exclusively for asynchronous WRITE event propagation between backend services.

### Technical Considerations

- The car registry service owns the car pool and inserts cars in the database. The car `id` is generated by the database that precise moment. Car booking is performed via the car `id`. Use UUIDs for database primary keys instead of auto-incrementing integers to prevent enumeration attacks.
- Any invalid car booking request must result in a 400 HTTP error response with a generic error message to prevent the provision of useful information on how to exploit the app to any malicious user.
- Use an MVP-scaled car view solution consisting of maintaining a copy of existing cars in the car booking service database to avoid a performance bottleneck when the latter service is requested to query the list of currently available cars.
- Use pessimistic locking at the database level to prevent double-bookings across car booking service instances.
- Implement the Saga pattern as payment failure fallback when a borrower has booked a car but they have insufficient balance in their account. Build an payment flow (booking -> payment -> confirmation) *orchestrator* within the car booking service instead following a decentralised (i.e., choreography-based) approach to ensure high-integrity and improve solution readability. The orchestrator must communicate with the payments service asynchronously, considering the booking as pending until it receives a payment confirmation from the payments service. Otherwise, it must cancel the booking due to insufficient funds.
- Implement separate Postgres schemas/databases for each service to strictly enforce service boundaries.

### Tech Stack

- The services must be implemented in Java with Spring Boot.
- The services' database must be Postgres.
- Services must communicate asynchronously via Kafka topics.
- Services must be accessible to users through Spring Cloud Gateway.
- Services, databases, and Kafka must be contenerised with Docker and orchestrated via Kubernetes.
- This app is not meant to be deployed into a cloud provider; the main execution environment is a local machine.
- The CI pipeline must be implemented for GitHub Actions; there is no CD for now.

### Technical Specification Document (TSD) Index

The expected index for the TSD is as follows:
1. **Overview**: provides a short definition of the app at hand as well as a list of core features and tech stack & infrastructure.
2. **Architecture**: defines a high-level architectural overview to explain the different components that compose the app and how they communicate with each other. Also, it explains the hexagonal architecture-based structure for each service and its relationship with its database.
3. **Functional requirements**: specifies the responsibilities of each service as well as the main flows considering the aforementioned business rules.
4. **Non-functional requirements**: lists a series of constraints in terms of performance, security, reliability, and maintainability.
5. **Data model and database schema**: for each aggregate it provides the create command for its corresponding table and an explanation for each field.
6. **Gateway API**: explains the gateway API endpoints following the Swagger standard definition.
7. **Potential issues and improvements**: provides two lists, respectively, to be considered during app development.

## Post-MVP Services

- **User Signup and Login**: Enables owners and users to register and login to the car sharing app and enforces authorisation in every single app request.
- **Car Tracking**: Enables app admins to track the position of all the borrowed cars.
- **Incidence Reporting**: Allows any user to report that a car is damaged. As a consequence, the car must be taken out of the available car pool and marked as damaged.
- **Notifications**: Notifies owners and borrowers of all sorts of events e.g., car booked, car damaged, etc.
- **Debtor and Offender Persecution**: Tries to get accumulated debt back from debtors and report offenders e.g., people not retuning booked cars. This service may be considered a generic subdomain, and thus may be obtained from a third-party.
